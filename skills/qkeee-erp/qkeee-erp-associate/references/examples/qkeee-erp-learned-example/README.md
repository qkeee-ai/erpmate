# Example: what `qkeee-erp-learned/<env-tag>` looks like

**This is a static example, not real captured data, and it was NOT
created via a live `skill_manage` call.** As a coding agent working on
this repo, this session has no running Hermes agent process to make that
call through — `skill_manage()` (see `hermes-agent/tools/skill_manager_tool.py`)
requires in-process state (the active profile's write-approval gate,
background-review provenance context, the security scanner) that only
exists inside a live `hermes-agent` runtime, not in this coding session.
Rather than fake that call or claim it was exercised, this directory
shows the exact file *content* the promotion plan (`erp_discover`,
action `promotion_plan`) hands to `skill_manage`/`memory` for a fictitious environment tag
`example-env` — generated by actually running
`memory_promote.build_promotion_plan()` against illustrative findings
(the code path this documents), then writing its outputs to plain files
here for inspection.

## What's here

- `SKILL.md` — the exact content of the `skill_manage(action="create",
  name="example-env", category="qkeee-erp-learned", content=...)` call's
  `content` argument.
- `references/environment.md`, `references/doctypes-catalog.md`,
  `references/custom-apps/crm.md`,
  `references/non-erpnext/example-payment-gateway.md` — the exact
  `file_content` argument of each corresponding
  `skill_manage(action="write_file", name="example-env", file_path=...,
  file_content=...)` call.
- `references/environment-partial.md` — what `environment.md` looks like
  when the catalog was built with gaps still open (`build_promotion_plan(...,
  gaps=[...])`): `catalog_complete: false` plus the gap list. A later
  session re-runs the failed steps instead of trusting it.
- `MEMORY-breadcrumb.txt` — the exact `content` argument of the
  `memory(action="add", target="memory", content=...)` call.
- `_skill_manage_calls.json` — the full ordered list of tool-call
  descriptors `memory_promote.build_promotion_plan()` returned, exactly
  as an agent turn receives them as the `result` of
  `erp_discover(action="promotion_plan", ...)`. This is the actual contract:
  an agent reads this JSON and issues each call itself via its own
  native `skill_manage`/`memory` tool access.

## Where this actually lands on a live profile

If this plan were executed for real against environment tag
`example-env`, the result on disk would be:

```
<profile>/skills/qkeee-erp-learned/example-env/
├── SKILL.md
└── references/
    ├── environment.md
    ├── doctypes-catalog.md
    ├── custom-apps/
    │   └── crm.md
    └── non-erpnext/
        └── example-payment-gateway.md
```

**Naming note (not a stylistic choice):** `qkeee-erp-learned/<env-tag>`
reads like a single slash-joined skill name. It isn't one —
`skill_manage`'s own name validation (`VALID_NAME_RE =
^[a-z0-9][a-z0-9._-]*$` in `skill_manager_tool.py`) rejects `/` outright.
The actual call uses skill_manage's separate `category` parameter:
`name="example-env"`, `category="qkeee-erp-learned"` —
`_resolve_skill_dir()` then nests it as
`<profile>/skills/qkeee-erp-learned/example-env/`, which is byte-identical
to `qkeee-erp-learned/<env-tag>` on disk. Only the in-memory tool-call
argument shape differs from a literal reading of that naming convention.
See `qkeee_erp.core.memory_promote`'s `learned_skill_name()` /
`learned_skill_manage_args()` docstrings for the same note in code.

## Regenerating this example

Call the tool with the illustrative findings (the shape is documented in
`build_promotion_plan()`'s docstring):

```
erp_discover(action="promotion_plan", tag="example-env",
             summary="Frappe 15.4/ERPNext 15.2 (illustrative example), custom app: crm",
             findings={"findings": {...}, "doctypes": [...], "custom_apps": {...},
                       "non_erpnext_systems": {...}})
```

The `result` is `_skill_manage_calls.json`'s content. Nothing is written
to disk by the plugin itself: the agent issues the calls (see
`qkeee_erp.core.memory_promote`'s module docstring for why).
